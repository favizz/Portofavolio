# Portfolio project notes

Astro (static output, no server) + Tailwind CSS v4 (`@tailwindcss/vite`) + GSAP/ScrollTrigger + Lenis smooth scroll. Deploys as plain static HTML/CSS/JS, no backend.

## Content policy

- Never use em dashes anywhere in generated copy or code comments. User preference, see the assistant's own memory system, apply a period/comma/colon instead.
- All personal/CV content must trace back to a real source (`CV_Favian Izza.pdf`, `Transcript_Favian Izza.pdf`, LinkedIn/GitHub, or explicit user instruction). Don't invent tech stacks, numbers, or company facts that aren't stated or aren't verifiable via web search. `dev/FACT.md` is the running source of truth, keep it updated when new real content is added.
- `dev/UPDATE.md` is the user's own scratch file for the next batch of instructions. Never edit it, only read and execute it.
- `dev/TASK.md` lists deliverables only the user can provide (real assets, missing personal facts). Keep it current: remove items once fulfilled, add new ones as they come up.

## Data model (`src/data/`)

Every section reads from a typed data file rather than hardcoding content in the component:
- `projects.ts`, `experience.ts`, `technology.ts`, `certifications.ts`, `education.ts`, `socials.ts`
- Each `projects`/`experience` entry has a `slug`, used as the DOM hook for the expand/carousel interaction and for cross-linking (see below).
- `experience[].tags` are only added when the CV literally names the technology (e.g. Siemens says "Laravel-based", so it gets `['Laravel', 'PHP']`, PHP because Laravel is a PHP framework by definition). Don't add tags based on guessing what stack a role "probably" used.
- `relations.ts` derives cross-links automatically from tag overlap: `findTechRelation(name)` finds the first project (priority) or experience with a matching tag, for making Technology tiles clickable. `findRelatedProject(tags)` finds the best-matching project for an experience entry's tags, used for Career's "see related project" button. If nothing matches, the UI simply doesn't render a link, that's intentional, don't force a fake relation.
- About's stat tiles are computed from `array.length`, not hardcoded numbers. Keep it that way, that's the whole point of it being "dynamic."

## The expand-to-carousel pattern (Projects, Career, Academic)

Shared markup contract per section:
```html
<div data-expand-grid data-expand-section="project|career">
  <div data-expand-carousel></div>
  <div data-expand-stage></div>
  <div class="contents" data-expand-default>
    <article data-expand-card data-slug="...">
      <div class="card-face">...</div>       <!-- shown in grid + stage -->
      <div class="card-detail">...</div>     <!-- shown only in stage -->
      <div class="carousel-face">...</div>   <!-- shown only in carousel -->
      <button data-expand-back data-expand-ignore>...</button>
    </article>
    ...
  </div>
</div>
```
`initExpandableGrids()` in `motion.ts` moves ONLY the selected card into `data-expand-stage` (real `appendChild`); the rest stay hidden in the default slot via CSS. The carousel container holds a STATIC list of `.carousel-item` label buttons (one per slug, rendered in the component, covering every item including the selected one); the active label is highlighted via `data-active`. A FLIP animation (`flipOne()` helper) smooths the card's move into the stage. Visibility of `.card-face` / `.card-detail` / `.carousel-face` is pure CSS keyed off the ancestor (`.expand-stage .card-detail { display: flex }` etc, see `global.css`), not per-card JS classes. Don't duplicate content between `.card-face` and `.card-detail`, if something needs to show only when expanded (like Career's company prestige note), put a low-visibility span inside `.card-face` itself and reveal it via `.expand-stage .role-note { display: inline-block }` rather than repeating the whole block in `.card-detail`.

Project, Career, and Academic all expand into a stage where the card becomes `display: flex; flex-direction: row` with a `.stage-media` column (40% width, capped at 340px, a real image: project screenshot, company logo, or school logo) and `.card-detail` filling the rest (`flex: 1 1 auto`), same rule in all three (see each component's scoped `<style>` block). Since Project/Career/Certification's collapsed hscroll cards also carry a fixed Tailwind width class (`w-[270px] md:w-[340px]`) for the row, and that class stays on the element when it's moved into the stage, `global.css`'s `[data-expand-stage] .expand-card` rule forces `width: 100% !important` to override it, otherwise the expanded card stays pinned at its collapsed width instead of filling the stage. Certification is the one exception: it has no carousel/stage/expand-card interaction at all (see Other conventions below), it only ever renders the collapsed row.

`initExpandableGrids()` also handles pin-only grids: if a `[data-expand-grid]` has `data-hscroll` but no `[data-expand-carousel]`/`[data-expand-stage]` children (Certification), the function still wires up the horizontal scroll pin (`createHscrollPin`, the `fonts.ready`/`load` resettle) and returns before touching any expand/click/label logic.

`data-expand-ignore` on an element (like the back button or the external "Visit site" link) stops its click from also triggering the card's own expand handler.

Cross-section links reuse the same system: any element with `data-open-section="project|career"` + `data-open-slug="..."` fires `initCrossLinks()`, which Lenis-scrolls to that section then dispatches a `portfolio:expand` custom event, which the matching grid picks up and expands. This is how About's highlighted keywords and Technology's clickable tiles jump to and open a specific card.

## Hero layout and the true-morph system

`Hero.astro` renders almost nothing of its own now, just the photo. Every piece of "Hero content" (the FAVIAN name, the nav links, the bio tagline, the project/experience stats) is literally `SideNav.astro`'s own DOM elements, FLIP-transformed (translate + scale, `scrubFlip()` in `motion.ts`) from a computed Hero-time position/size down to `transform: none`, their natural resting spot in the sidebar, scrubbed to Hero's scroll range. This is a real morph (the same element moving), not two separate pieces of markup cross-fading into each other, `initHeroFlip()` in `motion.ts` owns it:

- **Name -> FAVIAN**: `SideNav`'s small `[data-morph="name"]` span scales up to the SMALLER of a width fit (fills the viewport width between two 2rem side gaps) and a height fit (`vh * 0.42` minus the top gap minus the nav row that sits beneath it). Positioned `top: 2rem` (NOT vertically centered, unlike the flanking desc/stats below), so its bottom edge is a real, predictable anchor for the nav row. Centered horizontally, so it visually sits behind the photo (its z-index, and the whole sidebar's, is `4`, below the photo's `6`, intentional: "FAVIAN behind the picture" is correct/wanted, only the nav links must never touch the picture, not the name).
  - **The height budget is a share of the VIEWPORT, not of the space above the photo, and this ordering matters.** An earlier version measured the photo's live `top` (`10vh`) and fit the name into whatever was above it. That's a circular constraint that collapses: `10vh` is ~70px, so once the nav row was reserved the fit floored at the sidebar's 16px resting size and FAVIAN shipped as a caption-sized speck at the top of the page. The dependency now runs the other way, name and nav row are laid out first and the PHOTO's `top` is set beneath them (next bullet). If you ever need to re-tune the name's size, change the `0.42`, never reintroduce a read of the photo's position here.
  - This is a genuine trade-off, not a free win, and worth understanding before "fixing" it: "Favian" is ~3.4:1, so a full-viewport-width FAVIAN is ~400px tall on a 1366px-wide screen, which plus a nav row leaves under 40% of a ~750px viewport for the photo. Full-width FAVIAN + nav beneath it + a large photo is geometrically impossible in one viewport; `0.42` is the chosen balance (dominant wordmark, readable nav directly beneath, photo still the largest element).
- **The photo's `top` is DRIVEN by that layout**, set from JS to `nav row bottom + 16px`, so neither FAVIAN nor the nav links can collide with it at any viewport size and the photo still gets every remaining pixel of height (it's `position: fixed` with `bottom: 0`, so height = `vh - top`). Static per build, recomputed only on resize, never tied to scroll, so it doesn't violate "the photo must never visibly move". `Hero.astro`'s `top: 10vh` is now only the pre-JS fallback; the `@media (max-height: 700px)` override it used to carry is gone (it was a hardcoded guess at one screen size, this is exact at every size).
- **Nav links -> row beneath FAVIAN**: each `[data-morph-link]` moves from a horizontal row slot at `nameHeroBottom + 16px` (computed from the name's own Hero-time rect, NOT an independent fixed `top: 2rem`), evenly distributed across the same full-gap width, down to its stacked position in the sidebar's link list. They use `scrubMove()` (explicit **uniform** scale from a font-size ratio) and NOT `scrubFlip()`: because each link carries `w-full`, its resting box is the whole sidebar column, so `scrubFlip`'s `first.width / last.width` compares the link's TEXT width against its CONTAINER width, comes out below 1, and scales the links DOWN into unreadable specks (this shipped once). Reach for `scrubMove` for any morph target whose resting box isn't its visual content box.
- **Desc / Stats -> flanking text**: `[data-morph="desc"]`/`[data-morph="stats"]` scale up in place to the left/right flanks of the photo, vertically centered on `vh * 0.835` (the middle of the viewport's bottom third, not `vh * 0.5`), a deliberate placement below the photo's midline rather than dead-center.
- Each morph target's `color` is ALSO scrubbed (white at Hero, black at rest, via `scrubColor()`), independently of the transform, because sidebar panels are white-background/black-text (see Side navigation below) and black text would be invisible against Hero's pure black background mid-morph. Their own descendants (e.g. the stat number/label spans) carry no color class of their own, so they inherit the live-animated color from the morph target ancestor, don't add a `text-black`/`text-black/NN` class back onto them, it would stop inheriting and go invisible during the morph.
- Panels (the white background boxes) aren't part of the morph, since there's no Hero equivalent for "a white box", they scrub their own `background-color` from transparent to white over the same range instead. Content with no Hero counterpart at all (company marquee, email, contact button, all `data-hero-fade`) just fades in (opacity) over the final ~40% of the range.
- The whole measure-and-build step is wrapped in a `build()` function inside `gsap.context()`, called once at init AND again from a debounced (`200ms`) `window resize` listener (`ctx.revert()` first, to kill the previous run's tweens/triggers before rebuilding), instead of the one-shot `gsap.matchMedia('(min-width: 768px)')` callback an earlier version used. This is what makes the dual-fit sizing above actually dynamic rather than a calculation baked in once at load, a desktop window resize (or a tablet rotating) gets the FAVIAN/nav/desc/stats geometry recomputed for the new viewport. Below `768px` width the context is reverted and nothing is rebuilt (mobile uses `Header.astro`'s hamburger instead, the sidebar is hidden entirely there).

Several real bugs came up building this, worth knowing if this area ever needs touching again:
- **CSS `transform` has no visual effect on `display: inline` elements** (a bare `<span>` or `<a>`, the default). This was the actual cause of FAVIAN rendering at its tiny resting size instead of scaling up: `[data-morph="name"]` is a `<span>`, so the FLIP transform was silently a no-op, GSAP set the inline style, `getComputedStyle` even echoed it back, but nothing painted, confirmed empirically by toggling `display` live and watching the rendered rect jump from ~60px to ~1600px wide. `scrubFlip()` now checks `getComputedStyle(el).display === 'inline'` and forces `inline-block` before measuring/animating. Flex children still report `inline` from this check even though the flex algorithm blockifies them for layout, so the check still has to run for them, `<p>`/`<div>` targets (desc, stats) were unaffected since those default to `block`. One exception never got root-caused: a `<a>` that's a **direct** child of a flex container (the footer's Contact-Me button) kept rendering `matrix(1,0,0,1,0,0)` no matter what, tried inline vs block, wrapping it in a non-flex div, and removing `.btn-interactive`'s `transition: transform`, all failed, so that specific morph was abandoned in favor of a color/opacity-only treatment, see Side navigation below.
- **An `overflow: hidden` ancestor clips a transformed descendant that visually moves outside it**, even though `getBoundingClientRect()` still reports the moved/scaled box correctly (rect math doesn't know about ancestor clipping). This was why the stats block was reported "not visible": `[data-morph="stats"]`'s own parent panel had `overflow-hidden` (left over from an earlier version where the panel itself clipped the marquee), so once `scrubFlip` translated stats out to the Hero position, the panel clipped it to its own tiny sidebar-sized box, invisible everywhere else. The stats wrapper already has its own `overflow-hidden` for the marquee's sliding track, that's sufficient, the ancestor panel doesn't also need it, and mustn't have it. If a future morph target's content mysteriously vanishes despite correct transform math, check every ancestor for `overflow: hidden` first.
- **Implicit DOM-order stacking wasn't reliable at the scale FAVIAN uses (22x+)**: even after the display fix, the huge name box sometimes painted over the smaller, later-in-DOM stats box instead of ceding to it (confirmed with `elementsFromPoint`). Each morph target now gets an explicit `position: relative` (z-index only applies to positioned elements, `static` elements ignore it even with a transform-created stacking context) plus `z-index` (name: `0`, everything else: `1`), don't drop either half of that pair.
- **GSAP wants a fresh `scrollTrigger` vars object per tween.** Reusing the same object literal across multiple `gsap.fromTo()`/`gsap.to()` calls silently breaks all but the first, only one exhibited a visible transform, no console error. The fix is a small factory (`heroTrigger()`, `footerTrigger()`) that returns a new object each call, use that pattern for any new scrubbed tween, never `const scrollTrigger = {...}; gsap.fromTo(a, ..., {scrollTrigger}); gsap.fromTo(b, ..., {scrollTrigger});`.
- **`scrollWidth` is unreliable on `display: inline` elements**, it reported `0` for the name span and silently skipped the whole width-fit calculation. Measure with `getBoundingClientRect().width` instead, which works regardless of display type. Similarly, an element with `w-full` (relative to its own container) reports that container's width from `getBoundingClientRect()`, not its own content's width, the nav links' Hero-time spacing math temporarily overrides `width`/`display` inline before measuring, then restores them, to get the link's true text width.
- **A maximized 1366x768-class laptop screen nets well under 700px of actual viewport height once browser chrome is subtracted, this is common, not an edge case**, and at that height the photo's default `top: 10vh` (~65-70px) leaves too little room for FAVIAN plus the nav row beneath it, even at their smallest sizes. Fixed two ways together: `Hero.astro`'s `.hero-photo-fixed` bumps its baseline `top` to `18vh` under `@media (max-height: 700px)` (a static CSS value the photo settles at, never scroll-tied, so this doesn't violate "the photo must never visibly move"), and the name's height-fit math (above) floors at the sidebar's resting font size with a 4px safety margin so it degrades gracefully instead of shrinking toward zero on anything shorter still. Verify with `nameRect.bottom <= photoRect.top` and every `linkRect.bottom < photoRect.top` if this area regresses, sampled at a real short-viewport size, not just a tall one.

The photo (`.hero-photo-fixed`, `data-hero-photo`, `position: fixed`, centered on x, `top: 10vh; bottom: 0` (`18vh` under `700px` viewport height, see above), so it's strictly ~90% of viewport height with air above the head on normal screens) is pinned to the viewport, not the page, scrolling never moves it. `initHeroMorph()` owns its `opacity`/`filter` only (no `y`/`scale`, it must never visibly move, only blur and fade in place): a one-time `gsap.from` entrance, then a `gsap.fromTo` scrubbed to Hero's scroll range. Because this element owns opacity for the whole Hero lifetime, `[data-hero-photo]` must never also carry `class="reveal" data-reveal`, that races `initReveals()` for the same property (this exact bug happened once, verify with `getComputedStyle(photo).opacity` sampled at 0/25/50/99% scroll if this area regresses). There's no ring/glow/drop-shadow and no orbiting tech-icon ring around it (`initOrbit`/`data-orbit` were removed outright), both read as the "circling border effect" an earlier round explicitly asked to remove. It uses the full-silhouette background-removed cutout (`public/images/profile-cutout.webp`), sized via `height: 100%` on the `<img>`, `width: auto`, so the full body is always visible and never cropped.

## Side navigation

`SideNav.astro` is a fixed `left-2 lg:left-3 top-1/2 -translate-y-1/2` column (`hidden md:flex`, `w-[clamp(13rem,16vw,17rem)]`, responsive width so it never needs `overflow`, keep it that way if adding content, don't reintroduce a scroll fallback), z-index `4` (see above, intentionally below the photo). Every panel shares the SAME uniform white background (`.nav-panel`, animated in via `initHeroFlip`'s panel loop) with black text, not the differently-tinted segmented panels an earlier round used, that was explicitly reversed:
1. "Favian" (the name morph target) + the bio tagline below it. No phone icon (removed per instruction, the real number still lives in `dev/FACT.md` if it's ever needed again).
2. A spinning marquee of 4 stats (Projects, Experiences, Certs, Achievements, all `array.length`, no fabricated numbers), same endless-track technique as the company marquee below it.
3. The section nav links (the link morph targets), each a `nav-link` with a `hover:bg-black/5` fill.
4. An endless horizontal marquee of the real company logos from `experience[].logo`, each normalized to the same `h-7` box. Both marquees render THREE copies of their list (`[...items, ...items, ...items]`) and are **driven by GSAP in `initMarquees()` (motion.ts), NOT by a CSS `@keyframes` animation.** That distinction is the whole fix for a bug that survived several rounds of "but the CSS is correct": `@media (prefers-reduced-motion: reduce) { animation: none }` silently disables a CSS animation, and that pref is on far more often than it looks, **Windows 11 sets it whenever "Show animations in Windows" is off** (a common system setting) and it is force-enabled in this project's browser-automation environment, so the user's real browser AND every automated check both showed a correct-looking DOM with nothing moving. GSAP tweens ignore that pref, so driving the track from JS makes the motion actually happen. `initMarquees()` translates the track by exactly `scrollWidth / 3` (one copy, measured at run time, which is what makes the loop seamless) with `repeat: -1`, re-measuring on `fonts.ready` and `load` since web fonts and logo images both change the track's real width after first paint.
   - The GSAP `x` goes on `.marquee-track` itself; the stats marquee's FLIP goes on its separate `data-morph="stats"` WRAPPER. Never put both on the same node. That wrapper also owns the marquee's `overflow: hidden`, and the `.nav-panel` it sits inside must NOT also carry `overflow: hidden`, an ancestor with that property clips a FLIP-transformed descendant to the ancestor's own (tiny, sidebar-resting) box once the descendant visually moves outside it, see initHeroFlip's bug notes above, this was a real regression once.
   - **Verifying marquee motion in this environment is not possible by sampling `transform` over time.** The automation tab runs backgrounded (`document.hidden === true`), and Chrome pauses `requestAnimationFrame` there, so GSAP's ticker never advances and any before/after `transform` comparison reads "frozen" no matter what. Confirm `requestAnimationFrame` tick count first (it will be 0) before concluding anything; verify the mechanism instead (three copies present, GSAP `x` equal to `-scrollWidth/3`, no `animation` property left on the class).
5. Clicking the email (`[data-copy-email]`) copies it to the clipboard instead of opening a mail client, `initEmailCopy()` swaps the button's own text to "Copied to clipboard" for 2s as feedback, no separate toast element.
6. A boxed "Contact Me" button (`[data-morph="contact"]`, `href="#contact"`), the one boxed button besides CV/form-submit.

Active section is highlighted via the same `[data-section]`/`initActiveSection()` wiring the old header dots used. `Header.astro` is mobile-only (`md:hidden`). `.section` in `global.css` reserves `padding-left: 18rem` (`19rem` at `lg`) so content never sits underneath the sidebar, keep in sync if its width/position ever changes. No idle-hide system, don't add one back.

As the footer arrives, `initFooterMorph()` fades every sidebar panel except the contact button to opacity 0, while the contact button itself loses its boxed styling (solid black background, white text scrub to transparent/accent-blue text) before its own opacity fades out slightly later, once Footer's own real Connect section has visually taken over. An earlier attempt tried to literally FLIP the button's position on top of Footer's "Connect" heading (matching the Hero morph technique), but `footerConnect` isn't `position: fixed`, so its viewport position keeps changing as you scroll, and a live per-frame re-measurement inside a plain `ScrollTrigger.create({ onUpdate })` kept getting its own transform reset to identity on the very next tick by something never fully root-caused (reproduced even with a manual, non-GSAP `element.style.transform` set, so it wasn't a GSAP/vars-object bug, root cause presumably specific to that anchor's own CSS but not worth the further debugging time against how cosmetic this feature is). The color/fade version above avoided the whole class of bug and reads as "the button becomes text, then the real Connect section is there," which is a reasonable proxy for "turns into the CONNECT text."

This trigger's exact `start`/`end` anchoring went through two real, previously-undiscovered bugs, worth knowing if this area ever needs touching again:
- **Anchoring `start`/`end` to a section's `bottom`/`top` edge only works if there's enough real page length left below it for that edge to actually reach the target percentage.** An earlier version used `trigger: contact, start: 'bottom 55%', end: 'bottom top'`, reasoning that Footer directly follows Contact with no gap so `footer.top === contact.bottom` always. That equivalence is true, but it doesn't make the target reachable: Footer's own real content height is often shorter than one viewport (measured ~494px vs a ~748px viewport, a normal footer, not a bug), so the document's true max scroll lands with `contact.bottom` stuck well above 0, the tween's progress never reaches 100%, and the whole morph freezes partway (sidebar panels stuck translucent, button stuck ghosted) for the entire time Footer is on screen, confirmed empirically by sampling opacity across the full scroll range down to `document.documentElement.scrollHeight - window.innerHeight`. The fix: anchor BOTH `start` and `end` to `footer` itself (`start: 'top 90%'`, `end: 'bottom bottom'`), not `contact`. Footer's `top` edge is guaranteed to reach `vh - footerHeight` at true max scroll (Footer is the last element on the page) and `top 90%` only requires Footer to be at least 10% of the viewport tall to be reachable, trivially true for a real multi-column footer; `bottom bottom` (Footer's bottom edge reaching the viewport's bottom) is mathematically guaranteed to align exactly with true max scroll regardless of Footer's height. Since both points are on the SAME trigger element, their relative order is guaranteed correct by construction, no separate `endTrigger` needed. If a future range on this trigger ever needs re-tuning, prefer `top X%` (small `X` requires a taller footer) or `bottom bottom` over anything phrased against `contact`'s edges.
- **The fade targets the SIDEBAR WRAPPER's opacity (`[data-side-nav]`), not each panel's.** Fading the panels individually put a second writer on a property `initHeroFlip` already owns for the two `data-hero-fade` panels (company marquee and email, which scrub 0→1 across Hero). Two scrub tweens on the same property of the same element don't compose, whichever rendered most recently wins and sticks, and the footer tween records its own "from" value the first time it renders, which for those panels could be their `opacity-0` markup default. That was the actual cause of **"the company logos and email disappear from the sidebar when scrolling back up"**: on the way up the footer tween re-rendered its recorded `0` over Hero's intended `1` and they never came back. The wrapper is never a target of any `initHeroFlip` tween, so it has exactly one writer, and fading it takes the whole sidebar (panels, marquees, links, button) in one stroke without touching any child's properties. For the same reason the contact button now gets ONLY a color scrub here, never an opacity tween. Verified by probing the same scroll positions descending and ascending and confirming the two hero-fade panels read opacity 1 both ways.
- **The contact button's separate opacity fade-out and Hero's own `data-hero-fade` fade-in both target the SAME `opacity` property on the SAME element** (the button carries `data-hero-fade`, fading 0→1 across Hero, AND has its own later fade-out near Footer). A `.to()` (not `.fromTo()`) captures its "from" value once, at creation time, page-init time, while the button still sits at its markup default (`opacity-0`, before Hero's own tween has ever rendered a scroll-linked value for it). That captured `0` (or, if written as `fromTo({opacity:1}, ...)` without `immediateRender: false`, a captured `1`) then renders ONCE immediately at creation and sticks (an inactive scrub tween's last render doesn't get re-applied on unrelated scroll frames), silently overriding Hero's fade-in for the ENTIRE middle of the page until this tween's own active window is finally entered near Footer. The fix is `gsap.fromTo(contactBtn, {opacity:1}, {opacity:0, immediateRender:false, scrollTrigger:{...}})`: the explicit `{opacity:1}` "from" is only ever actually rendered once scroll enters this tween's own start/end range, `immediateRender:false` suppresses the stray render-on-creation, leaving Hero's tween in sole control everywhere else. If a future morph target needs two independently-scrubbed tweens on the same property across non-overlapping scroll ranges, this is the pattern, verify by sampling the CSS property at several points spanning BOTH tweens' ranges, not just the range you just touched, a bug in one can silently show up as wrong behavior in the other's territory.

`initExpandableGrids()` must run before `initFooterMorph()` in `init()`'s call order: it's what creates the hscroll pin-spacers (Project, Certification, Career), and those spacers grow the real page height significantly. `initFooterMorph`'s triggers are string-based positions (`'top 90%'` etc), calculated once at creation time against whatever the document height is AT THAT MOMENT, if it ran first, Footer's trigger would be positioned against a document thousands of pixels shorter than the real one, firing the whole footer morph as early as partway through Project. The exact same class of bug as the Lenis pin-spacer-staleness one below, just for a different consumer of page geometry.

## Section separators

`.section + .section` in `global.css` draws a solid 1px top border (`var(--color-primary-strong)`, not a low-opacity wash) between adjacent sections, a deliberate visual break so each section reads as its own "page" even though the scroll motion itself stays smooth (Lenis) and section backgrounds still cross-fade via the gradient system below. Don't remove this thinking it conflicts with "seamless scroll", the two are orthogonal: motion is seamless, boundaries are visually clear.

## Section sizing

`.section` is `height: 100svh` (exact, not `min-height`) with `overflow: hidden`, every section, expanded or not, must fit inside exactly one screen with nothing requiring an in-section scroll to see. `overflow: hidden` here is deliberate as a forcing function: if a section's content ever grows taller than the viewport, it gets silently clipped instead of pushing the next section down or growing the page, which is an intentional trip-wire, if you see clipped content while testing a change, that's the signal to shrink text/spacing in that specific section rather than to remove the `overflow: hidden`. When adding content to any section (including the `.stage-media`/`.card-detail` expanded layout or a new hscroll card), verify with `section.clientHeight` vs `section.firstElementChild.scrollHeight` at a real viewport height, not just visually, a few pixels of overflow is easy to miss by eye.

## Color policy

The page background is flat black (`GradientField.astro` is now just a single `bg-bg` div, no blobs, no grain, no scroll-driven color-cycling, that was explicitly asked to be removed outright: "totally black, I just want to see"). Section headings all use the single `text-accent` token (via `.section-heading`, see Typography below), not per-section rainbow hex values, including About's heading which used to be the one straggler on `text-primary-strong` (a dark blue close to the near-black background, a real low-contrast bug, not just an inconsistency). The sidebar is a deliberate, scoped exception to the dark palette: white panels, black text (see Side navigation above), don't "fix" that thinking it violates the black/dark-blue/white rule, it's still within that same restricted palette family, just inverted for that one component.

Decorative background flourishes were stripped out entirely, they were adding visual noise without conveying information: `GradientField.astro`'s twinkling `.stars` layer is gone (the blobs + grain noise stay, that's the intentional background system), Hero's blur-circle/dashed-ring behind the photo is gone, About's rotated-square/white-ring frame around the profile photo is gone, and each section's ambient SVG decoration is gone (About's `.nebula` radial gradient, Career's `.flight-path` dashed line, Projects' `.constellation` lines, Technology's `.orbit-rings` dashed circles). Don't add a new one of these per-section "ambient" decorations without a specific reason, the whole category was a deliberate removal, not an oversight.

The `.glow-border` class (border + accent box-shadow on hover) was renamed to `.hover-border` and the box-shadow dropped, it's a plain border-color hover transition now. Same for `.btn-interactive`'s hover/active states, the box-shadows are gone, only the transform lift/press remains. The expanded-card border glow (`[data-expand-stage] .expand-card`'s box-shadow) is gone too. If you're tempted to add a glow/shadow-based hover effect anywhere, don't, that's the exact effect that was removed.

Technology's section used to be the only one centered (`items-center text-center`) while every other section is left-aligned, that inconsistency is fixed, Technology now matches the rest (`items-start text-left`). Contact got the same fix (its heading/paragraph/form container were `items-center`, now `items-start text-left`), the form itself still uses `mx-auto`-free left-aligned layout, inputs keep their own internal `text-left` labels.

## Typography

Every section (About, Academic, Certification, Projects, Technology, Career, Achievement, Contact) uses the SAME eyebrow-label + heading pattern, not a plain section-name `<h2>`: a small uppercase eyebrow holding the plain section name (`text-sm font-semibold uppercase tracking-[0.3em] text-accent`, styled inline since it's only ever used once per section, no dedicated class), followed by an `.section-heading` element holding the section's one real descriptive sentence (e.g. Academic: eyebrow "Academic", heading "Formal education behind the systems I build."). `.section-desc` (the old single-line, ellipsis-capped intro class) no longer exists, it was fully replaced by this pattern and deleted as dead CSS once nothing referenced it.

`.section-heading` (`clamp(1.75rem, 3.2vw, 2.75rem)`, fluid with viewport width instead of jumping at a breakpoint, hard-capped to 2 visible lines via `-webkit-line-clamp: 2` regardless of viewport width or sentence length) is sized for this new role. An earlier version of this class was sized much larger (`clamp(2.75rem, 6vw, 4.5rem)`, uncapped) for its ORIGINAL role, holding just the plain short section name (a single word, never wrapped). Once every section started feeding it a full sentence instead, that combination reliably wrapped to 3-5 lines at that size and blew every section's `100svh` budget (measured: Achievement overflowed by 227px, Projects by 194px, Career by 165px, About itself already by 68px even before this round's changes, at a real short-viewport laptop height). Don't push the clamp() ceiling back up or drop the line-clamp without re-verifying every section still fits at a real short-viewport height (`section.clientHeight` vs `section.firstElementChild.scrollHeight`, see Section sizing above), a tall viewport alone won't reveal this class of regression.

About's longer narrative bio paragraph isn't line-clamped like `.section-heading` (it's meant to be read in full), but still needs to shrink rather than hit `.section`'s `overflow: hidden` on short viewports, it uses `.section-body` (`clamp(0.85rem, 1.6vh, 1.25rem)`, viewport-HEIGHT-based since the failure mode there is specifically vertical overflow). When touching heading/intro/bio markup, reuse these classes (eyebrow's inline utility string, `.section-heading`, `.section-body`) rather than reaching for `text-6xl md:text-7xl` or a fixed `text-2xl` again.

## Scroll-lock

`initScrollLock()` finds whichever section currently covers the most viewport area, and if that section's own TOP EDGE is misaligned by more than 4px but less than half a viewport, waits 125ms of continued stillness then Lenis-snaps its top to 0. Guards against fighting its own triggered scroll via an `isSnapping` flag, plus an 800ms cooldown after a snap completes. If this ever feels too aggressive, tune the 4px dead zone, the `0.5 * vh` outer bound, the 125ms delay, or the 800ms cooldown, don't rip the feature out.

**Aligning on the section's top edge deliberately replaces an earlier "is this section's own `h1`/`h2` between 40% and 60% of viewport height" test, and that swap is the fix for "the lock is inconsistent between scrolling up and scrolling down."** That band is a thin ~20%-of-viewport window a heading only passes through if you happen to stop scrolling at the right instant, and because the heading sits near its section's TOP rather than its middle, the heading entered the band at a different scroll position going down than coming back up, so scrolling up frequently skipped the snap entirely. Top-edge alignment is symmetric by construction: the same target scroll position from either direction, and every section qualifies somewhere on the way past it with no timing luck involved (verified by probing identical scroll positions in both directions and diffing the decision, they now match exactly). Pinned hscroll sections (Project, Certification, Career) are self-exempting while pinned, GSAP holds them at `rect.top === 0` for the whole pin, already inside the 4px dead zone, so no snap fires and the horizontal scroll is never interrupted.

## Lenis's scroll limit vs GSAP pin-spacers

`new Lenis(...)` in `initSmoothScroll()` measures the page's scrollable height ONCE, synchronously, at construction, before `initExpandableGrids()` (called later in the same `init()`) creates the hscroll pins. Each pin inserts a GSAP pin-spacer into the document to reserve its own scroll distance, which grows the real page height well past what Lenis already measured, so `lenis.limit` permanently undershoots the true max scroll by roughly the combined height of every pin-spacer (measured once as 5286 vs a true 9341, a ~44% shortfall) unless something tells Lenis to re-measure. This was the actual cause of "clicking a nav link deep in the page leaves the previous section still visible": `lenis.scrollTo(target)` silently clamps to the stale `limit`, landing short of the target instead of erroring. Fixed two ways, keep both: `ScrollTrigger.addEventListener('refresh', () => lenis.resize())` in `initSmoothScroll()` (covers every future refresh: window resize, expand/collapse's `deferredRefresh()`, font load) plus one explicit `lenis.resize()` on the next animation frame at the end of `init()` (covers the very first scroll, before any refresh has had a reason to fire yet). If a similar "scroll stops short" bug ever resurfaces, check `window.lenisInstance.limit` against `document.documentElement.scrollHeight - window.innerHeight` before assuming it's the scroll-lock or a target-calculation bug. Related: `.section` no longer sets `scroll-margin-top`, an old `5rem` value from a since-removed top-header design was making every programmatic/anchor scroll stop 80px short on purpose, compounding the same symptom.

## Other conventions

- Directional/navigation actions use `.text-cta` (highlighted text + arrow, e.g. "Visit site →", "← Return"), not boxed buttons. Boxed buttons are reserved for primary CTAs (CV, form submit). The CV download button lives in `Footer.astro`'s Connect column (moved out of Hero, which is text-free now).
- Certification does not expand. `Certifications.astro`'s cards are plain, non-interactive (`article`, no `data-expand-card`/`role="button"`/click handler) with a real `.text-cta` "View document" link straight to the certificate's document (`certifications.ts`'s `documentUrl` field, real Google Drive links for the three real certs sourced from `dev/FACT.md`'s verified CV hyperlink file IDs, `https://google.com` placeholder for the two `dummy: true` carousel-filler entries). It still keeps its `data-hscroll` pinned horizontal scroll (still nice for browsing many certs), just no click-to-expand-into-stage behavior, see the expand-to-carousel section above for how `initExpandableGrids()` supports this pin-only mode.
- Contact is a form (Name/Email/Subject/Message) whose submit opens a prefilled Gmail compose window (`https://mail.google.com/mail/?view=cm...`) addressed to the user. No backend, nothing stored; keep it that way unless the user picks a form service. The form itself has no `max-w-*` cap, it spans the section's full content width. Every text input/textarea carries `minlength`/`maxlength` (Name 2-80, Subject 3-120, Message 10-2000, Email capped at 254 per RFC), any new free-text input a visitor types should get the same treatment rather than being left unbounded.
- Projects/Certification/Career grids carry `data-hscroll`: collapsed state is a row of fixed-width nesh-style cards translated horizontally by vertical scroll. This lives inside `initExpandableGrids()` in `motion.ts` (not a separate function), via `createHscrollPin()`/`destroyHscrollPin()`: the section is GSAP-`pin: true`'d for the duration of the row's translateX, so the page cannot scroll past a still-animating carousel, it visually "finishes" the row before releasing the pin. The pin lifecycle is coordinated with expand/collapse: `expand(slug)` calls `destroyHscrollPin()` before the FLIP transition (the row layout changes entirely once a card is staged), `collapse()` rebuilds it via `createHscrollPin()` on the next two animation frames. Academic stays a numbered row list (`data-list`, no pin).
- Dummy carousel-filler entries in `projects.ts`/`certifications.ts` have `dummy: true` and are excluded from About's stats. Never let dummies leak into stats or FACT.md.
- The horizontal carousel's scrub is a pure function of absolute scroll position (GSAP `scrub: true`), so landing directly on a mid-scrolled section (hash link, refresh) already shows the correct offset with no "first visit" replay needed. Because web-font swap and late image loads can shift section heights and stale the trigger measurements taken at init, the hscroll setup re-runs via a `resettle()` (`destroyHscrollPin()` + `createHscrollPin()`) on `document.fonts.ready` and `window load` as a safety net, don't remove that.
- **There is deliberately NO scroll-driven card cycling inside an expanded grid, and no scroll hijacking while a card is expanded. Do not add either back.** An earlier version stepped to the next/previous card on `wheel` over the expanded region and suppressed page scroll while doing so (`data-lenis-prevent` on the grid to stop Lenis, plus `event.preventDefault()` to stop the browser's native scroll fallback, both were needed since Lenis checks `composedPath()` for that attribute rather than `event.defaultPrevented`). It was removed outright on explicit instruction after never behaving correctly at the boundary: the last card bounced back to the previous one and forward again repeatedly while ALSO releasing the page to scroll onward, so the user lost control of the carousel and the page simultaneously. Selection now changes only by clicking a carousel label, clicking a card, or following a cross-link. `data-lenis-prevent` is no longer set anywhere. The expanded layout still stacks carousel-above-stage in a column below `768px` and switches to the row layout at `md+`.
- `expand(slug)` behaves differently depending on whether a card is ALREADY expanded. First expand (from the collapsed grid): the full FLIP-from-collapsed-position animation via `flipOne()`. Cycling to a different card while one is already expanded (vertical-carousel wheel browsing): a plain cross-fade/slide (`opacity`+`y`), not another FLIP, because the outgoing card is `display: none` while hidden (only the staged card renders), so FLIP's "first" rect would be zero-size and the scale math degenerates into an instant snap instead of a visible transition, this was the literal cause of a "pops every time instead of only the first time" complaint. Keep this split if touching `expand()`.
- Pinned hscroll sections rely on `ScrollTrigger.config({ ignoreMobileResize: true, fastScrollEnd: true })` (set once, near `gsap.registerPlugin`, `fastScrollEnd` is cast to a locally-extended type since it's missing from this GSAP version's `.d.ts` despite being a real runtime option, see `node_modules/gsap/ScrollTrigger.js`). `ignoreMobileResize` stops a mobile address-bar resize mid-scroll from being treated as a real viewport change (which used to shorten pinned hscroll distances on phones). `fastScrollEnd` is GSAP's documented fix for a very fast flick blowing past a trigger's start/end in a single frame and leaving a scrubbed tween (Hero photo opacity, a pinned carousel) stuck mid-transition instead of resolving to its end state, don't remove either without checking both mobile hscroll and fast-flick scrolling first. The hscroll pin's own `end` also carries `+= window.innerHeight * 0.4` past the row's natural width, the same kind of deliberate dwell as the vertical carousel's boundary-hit count, reaching the last card holds the pin a bit before releasing.
- Back buttons in expanded cards are icon-only (`.back-arrow-icon`, a CSS `mask-image` using `public/images/icons/back-arrow.webp` recolored via `background-color: currentColor`), no "Return" text. List-style rows (Academic) don't get a hover arrow either, a bare arrow whose only job was hinting "this is clickable" was removed outright, the row's own hover background/color change already signals that. Directional CTAs with real label text (`.text-cta`, "Visit site →", "View document →", "See related project →") keep their arrows, those are a different thing (a labeled action), not a bare clickability hint.
- Programmatic scrolls must go through `scrollProgrammatic()` in motion.ts, which suppresses the scroll-lock while the tween is in flight. Cross-links scroll to the target `[data-expand-grid]` (the content), not the section heading.
- Browser-testing note: Lenis animates on requestAnimationFrame, which Chrome pauses in backgrounded tabs, so automated scroll verification in a background tab will appear frozen. Verify scroll targets by instrumenting `lenis.scrollTo` calls instead.
